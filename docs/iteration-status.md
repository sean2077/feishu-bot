## 产品目标

先在飞书＋原生 Claude Code 的既定场景做到比 cc-connect 更自然、可靠、易维护，而不是复制全部渠道和执行底座。对标以相同任务的实际体验为准：首次部署需要的人工步骤、多人补充是否完整进入会话、追问与附件是否好用、故障后是否知道如何继续、恢复是否避免重复副作用，以及同条件的延迟和资源占用。测试通过只证明所覆盖的契约；没有真实客户侧验收或同条件对照，不宣称已经整体超越。

### 关闭阶段的信息提示等待

[PR #55](https://github.com/sean2077/feishu-bot/pull/55) 针对 PR #54 审查时已标记的关闭边界：同聊天 `/stop` 虽已不再受无关提示网络请求阻塞，但 `Gateway.close()` 会等待所有已跟踪任务，因此一条永不完成的只读状态或无效输入回复仍可拖住服务关闭和状态库释放。测试先行提交 `4bb6f9b` 的 [CI 41499084178](https://github.com/sean2077/feishu-bot/actions/runs/41499084178) 在 Ubuntu Node.js 22.16／24 均复现两项新测试失败（关闭超过受控等待窗口）；其余既有核心用例通过。后续推送使前一轮 Windows 作业取消，因此不把该 red-phase 写成四平台完整结果。

实现 `d777fcb` 只给非持久 `notice` 增加关闭信号，重用现有 `waitOrAbort` 等待边界。关闭时先解除其网络等待，并在完成或失败结果迟到时跳过数据库访问；发送已经发出时不会把本地解除等待误称为远端撤销，也不自动补发。原生进程、审批与持久 outbox 仍沿用原规则，未添加全局请求超时或新的消息队列。实现版 [CI 41499317043](https://github.com/sean2077/feishu-bot/actions/runs/41499317043) 四组 Ubuntu／Windows × Node.js 22.16／24 全部通过，均完成完整检查、CLI help 与 3 样本／9 轮原生 fixture 基线。已读 Ubuntu Node24／Windows Node24 日志：核心 243 通过、1 项既有平台跳过，原生／进程 15 项通过。两个新增测试都在真实 Gateway／SQLite 与模拟不完成的飞书发送上完成关闭，再放行旧请求核实关闭后不索引。仍不是实际飞书客户端、真实网络套接字关闭或真实模型服务验收。

### 表情回执的服务关闭边界

[PR #56](https://github.com/sean2077/feishu-bot/pull/56) 复核上一批信息通知退出修复之外的持久表情链路：已记录 `attempt:processing` 的 OnIt 请求若网络始终无响应，原有 `Receipts.drain()` 会使 `Gateway.close()` 无法完成，进而拖住数据锁释放。测试先行 `1a33bae` 的 [CI 41507759029](https://github.com/sean2077/feishu-bot/actions/runs/41507759029) 在 Ubuntu Node24 复现新增测试失败：关闭在受控等待内没有返回，而既有核心测试通过。此处模拟无限期飞书反应请求，未使用实际飞书凭据。

修复在回执管理器内部只跟踪当前等待的网络请求，不保留历次完成调用的监听器；服务退出时本地解除等待，外部反应写入仍可能成功。任何未经确认的添加保留已有持久 `attempt:*` 状态，由重启后的归属查询对账，不改写为成功、不自动重复添加，也不让迟到结果访问已关闭数据库。中间版本曾将常规 `drain()` 错误地改成终止操作，[CI 41508186526](https://github.com/sean2077/feishu-bot/actions/runs/41508186526) 的 Ubuntu Node22 出现 17 项既有回执／交付测试失败；据此拆分仅关闭阶段调用的 `close()` 与保持原语义的 `drain()`，没有删除或放宽旧断言。最终实现、平台 CI 与合并状态以 PR 实际记录为准。真实飞书 API 调用与未知远端结果仍须独立验收。

### 流式预览的停止／关闭等待

[PR #57](https://github.com/sean2077/feishu-bot/pull/57) 复核持久表情关闭边界之外的预览卡片：`Render.flush()` 原先等待卡片创建／更新网络响应；`Render.cancel()` 再等待其串行尾部，可能使同聊天 `/stop` 和服务 `Gateway.close()` 一直受飞书慢请求阻塞。最终答案即使已事务保存，也可能在 `preparing` 状态被迫等待远端预览。

测试先行 `9f8be26` 的 [CI 41511913327](https://github.com/sean2077/feishu-bot/actions/runs/41511913327) 中，已读取 Ubuntu Node24 日志：两个新测试分别复现 `/stop` 与最终答案后关闭受阻，其他核心测试通过。测试使用真实 Gateway、SQLite 与刻意不完成的模拟飞书卡片请求；不假称实际平台网络故障。验收要求：关闭时只解除本地等待，不撤销已经发出的网络请求；未知新卡创建不能变为可自动重试的 `pending`，已知远端 ID 必须保留以恢复同一卡片；原生 session、事务答案和 Done 边界不变。

首次实现 `e9a79da` 在 [CI 41512165064](https://github.com/sean2077/feishu-bot/actions/runs/41512165064) 的 Ubuntu Node24 中让两个新测试通过，但旧 `result-persist` 的“关闭时远端刚返回已知 ID”测试失败：原先可恢复为 `pending` 的已知卡被误判 `uncertain`。据此修正为只延迟一个事件循环轮次释放本地预览等待，允许同轮已完成的响应保存远端 ID；真正悬置的写入仍按未知处理。没有增加网络超时、自动重复创建或弱化旧断言。取消卡片的外观更新改为不阻塞停止／关闭，但其远端最终显示仍属 best-effort。第三项回归另外覆盖已知卡片的悬置更新。最终 CI、审查及合并状态以 PR 记录为准。
