# 连续图片输入

默认 `limits.imageBatchMs = 0`，每条消息立即按原有流程独立交付。显式开启后，同一聊天、同一作者、同一会话、相同引用及线程关系的连续独立图片可在固定窗口内组成一次原生输入。富文本带图、文字和命令不作为纯图片合批。群里每条图片消息仍须单独满足触发条件并通过作者授权（默认明确 @；`mentionOptional` 群按作者授权），没有 @ 的消息不会被附近图片带入上下文。

```json
{
  "limits": {
    "imageBatchMs": 800,
    "imageBatchMaxImages": 8,
    "attachmentBytes": 20971520,
    "imageBatchBytes": 41943040
  }
}
```

这是合入主配置的可选片段。窗口最大 5000 ms，图片数量范围 2–12，批次总量最多 100 MiB；单文件仍受 `attachmentBytes` 限制。窗口从第一张接收时间起算，不因后续图片而延长。达到数量上限立即封闭批次；作者、引用或线程变化，以及文本、管理命令、compact 都是边界，不跨越合并或重排。审批回调独立执行，不等待图片窗口。

每张图片在自己的 inbox 行保存消息、作者、资源、UUID 和批次标记，窗口截止时间也在 SQLite 中。临时计时器仅唤醒已有输入派发，不是业务调度器。等待窗口不启动 Worker；派发时才下载资源并将完整批次组合为一个原生输入。任一下载失败、单文件或总量超限，整批明确取消并清理未完成的临时下载，不以部分图片执行任务。完整且通过单文件限制的只读缓存可以保留，供同一获准附件的后续读取或未发送输入恢复使用；缓存存在不等于模型已收到该批次。撤权时丢弃内容且不向无权成员发送提示。

原生仅收到一个批次输入，但收到消费和最终结果时网关会映射回每一条原消息；必要文件未确认送达前，任何成员消息都不能获得 Done。补发已保存的结果不重新执行看图任务。

`/stop` 和 `/new` 取消未交付批次；新会话不继承旧批次。服务重启会保留原会话和未发送批次，重新依据持久截止时间派发，不丢失已确认接收的图片。已经越过原生发送边界的整批输入恢复为结果未知，不自动重放。Worker 异常退出且清理已确认时，尚未发送的图片可在同一原生 session 续接；停止未确认则保留容量并阻止替代进程。

合批只改善输入归属和连续发图体验，不保证配置的模型具备视觉理解能力。真实飞书手机／桌面图片事件及模型视觉效果需独立验收。
