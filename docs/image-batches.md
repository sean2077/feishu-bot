# 连续图片输入

默认 `limits.imageBatchMs = 0`，每条消息立即按原有流程独立交付。显式开启后，连续发送的独立图片可在固定窗口内组成一次原生输入。本页说明合批规则与恢复语义；在对话契约中的位置见[消息完整性与附件](conversation-contract.md#消息完整性与附件)。

## 配置

```json
{
  "limits": {
    "imageBatchMs": 800,
    "imageBatchMaxImages": 8,
    "attachmentBytes": 20971520,
    "imageBatchBytes": 41943040
  }
}
```

这是合入主配置的可选片段，新增字段均可省略。窗口最大 5000 ms；`imageBatchMaxImages` 默认 8、范围 2–12；`imageBatchBytes` 默认 40 MiB、最多 100 MiB；单文件仍受 `attachmentBytes` 限制。

## 合批规则

- 只合并同一聊天、同一作者、同一会话且引用及线程关系相同的连续独立图片。富文本带图、文字和命令不作为纯图片合批。
- 群里每条图片消息仍须单独满足触发条件并通过作者授权（默认明确 @；`mentionOptional` 群按作者授权）。不能用前一条消息的 @ 为后续图片授权，没有 @ 的消息不会被附近图片带入上下文。
- 窗口从第一张图片的接收时间起算，不因后续图片延长。达到数量上限立即封闭批次。
- 作者、引用或线程变化，以及文本、管理命令和 compact 都是边界，不跨越合并或重排。只读管理命令可以封闭窗口但不主动派发任务，既有截止时间仍负责唤醒。审批回调独立执行，不等待图片窗口。

## 持久化与派发

每张图片在自己的收件记录中保存消息、作者、资源、UUID 和批次标记，窗口截止时间也保存在 SQLite 中。临时计时器只唤醒已有输入的派发，不是业务调度器。等待窗口不启动原生进程；派发时才下载资源，并把完整批次组合为一个原生输入，交给原生前将整批原消息一起标记为 sent。

任一下载失败、单文件或总量超限时，整批明确取消并清理未完成的临时下载，不以部分图片执行任务。已完整下载且通过单文件限制的附件文件可以保留，供同一获准附件的后续读取或未发送输入恢复使用；文件存在不代表模型已收到该批次。撤权时丢弃未发送内容，且不向无权成员发送提示。

## 结果归属

原生只收到一个批次输入，但消费和最终结果会映射回每一条原消息；必要文件未确认送达前，任何成员消息都不会获得 Done。补发已保存的结果不重新执行看图任务。

## 取消与恢复

- `/stop` 和 `/new` 取消未交付的批次，新会话不继承旧批次；`/cancel-input` 只能整批取消。
- 服务重启保留原会话和未发送批次，按持久截止时间重新派发，不丢失已确认接收的图片。
- 原生进程异常退出且清理已确认时，尚未发送的图片可在同一原生会话续接；停止未确认时保留进程名额并阻止替代进程。
- 已经越过原生发送边界、但没有结果的整批输入恢复为结果未知，不自动重放。

## 限制

合批只改善输入归属和连续发图体验，不保证配置的模型具备视觉理解能力。真实飞书手机／桌面的图片事件及模型视觉效果需独立验收（见[验证与验收](validation.md)）。
