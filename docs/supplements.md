# 运行中补充

`/btw 正文` 与 `/ps 正文` 是同义的网关命令，只向当前正在执行的前台任务补充信息；它们不是旁路问答，也不会作为同名 slash 命令交给 Claude Code。回复卡上的补充表单是同一机制的另一个入口。普通忙时输入保持原有行为。本页补充[对话行为](conversation-contract.md#运行中补充)中的规则细节。

## 目标与授权

- 群里每条 `/btw`／`/ps` 默认仍须由获准成员明确 @，`mentionOptional` 群按该群配置；私聊用户也须授权。卡片表单来自平台回调，按卡片绑定的房间、会话、轮次和操作者校验，不需要 @。
- 空参数显示用法。没有未完成的前台输入时明确拒绝，不创建会话、不启动原生进程、不调用模型；空闲热进程、仅有后台活动或正在执行 compact 都不算可补充的前台任务。
- 补充绑定接收时的那一个前台输入，不自动跟随下一任务。下载附件期间和交给原生前都会再次检查目标与授权。
- 补充保留独立 UUID、消息 ID、作者、引用、线程和附件，经原有收件、去重、限速和容量控制交付。`/btw /new` 和 `/ps /compact` 的正文是文本，不执行管理命令；补充也不回答审批、不扩大工具权限。

## compact 边界

已排队的 `/compact` 是边界。其后的补充先保存并明确提示等待，不能越过边界；等待期间审批卡片仍可操作。目标在等待中结束时，补充按下文取消，不会在压缩后作为新任务执行。

## 宿主交接与回执

原生宿主在交接时再次检查目标：收到补充时若已观察到目标的原生结果，就在写入原生输入队列之前拒绝。即使网关状态因异步事件处理暂时落后，这种已知失效的补充也不会被提交为新任务。

只有收到原生宿主的接收确认才发送补充回执，仅完成管道写入不发回执，重复确认不重复回执。卡片表单的回执显示提交者和完整正文（引用格式），`/btw`／`/ps` 的回执只标注提交者。回执只表示已交给原生输入流，不代表模型已经读取、理解或执行；原生可能在工具完成后才读取。

明确的入队前拒绝会把对应的 sent 补充与取消通知一起持久保存，不产生模型结果、用量或 Done；普通输入、已确认接收的补充和其他会话不受影响，通知仍按当前授权交付。若拒绝尚未持久化就发生故障，恢复时保持结果未知，不推断已经取消，也不自动重放。这个边界不承诺撤回已进入原生输入流的内容，也不把接收确认当作模型消费证明。

## 取消与恢复

- `/stop`、`/new` 和恢复其他历史会话都会取消尚未交付的补充。
- 目标结束或原生进程意外退出时，绑定旧运行的待交付补充取消，并发送持久的系统恢复通知。
- 服务重启时即使保留相同会话，也不会把旧补充恢复成新任务。
- 已经发送而结果未知的补充按通用规则标记 uncertain，不自动重放。

## 回复归属

补充本身不创建独立的答案卡。正常回复沿用本轮卡片，按原生结果 UUID 分别完成归属消息；只有结果成功且最终卡片和必要文件全部送达，才添加 Done。取消通知属于系统恢复提示，不是模型答案。
